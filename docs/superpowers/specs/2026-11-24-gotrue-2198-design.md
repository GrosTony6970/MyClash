# GoTrue 2.195 → 2.198 — design (small change)

Status: proposed 2026-11-24. Branch `feat/mcp-server` (PR #110), its own commit, before slice 2.

## Why

On GoTrue 2.195 a Claude connector token (an OAuth-server access token) can call GoTrue's own
`PUT /auth/v1/user` (password and email change), `/user/identities`, `/user/oauth/grants`,
`/factors`, `/logout`. MyClash's wall (MCP spec, call A) cannot reach GoTrue. 2.198 restricts OAuth
client tokens to the OAuth endpoints plus read-only `GET /user` (`403 no_authorization` otherwise).
This closes the MCP spec's Review Focus 1 / operator decision 1 before OAuth goes live.

## Goals

- `infra/docker-compose.prod.yml` and `infra/docker-compose.dev.yml` run `supabase/gotrue:v2.198.0`.
- Every place the API pins a GoTrue answer still holds on 2.198 — proven against a real 2.198, not
  assumed.
- The connector e2e records the new refusals.

## Non-goals

- No other Supabase service bumped (realtime, storage, PostgREST, postgres stay as they are).
- No use of 2.196–2.198 features (MFA recovery codes, SCIM, passkeys).
- No move of anything to `GET /oauth/userinfo` (MyClash never calls `/user` with a connector token).

## Constraints

- Timing: 2.198.0 is 8 days old (published 2026-11-16), but Supabase's own self-hosted
  `docker/docker-compose.yml` pins `supabase/gotrue:v2.198.0` — taken as the soak signal. Claude's
  call; the operator may hold the merge until 2026-11-30.
- Releases crossed: 2.196 (email identity created on first password set, behind an experimental
  flag for the user path; email-change and identity-unlink fixes), 2.197 (MFA recovery codes, SCIM
  tables, `one_time_tokens.expires_at`), 2.198 (OAuth-token restriction; password cleared on recover;
  one-time tokens become the source of truth; legacy null-aal sessions invalidated; after-user-created
  hook only on creation). GoTrue migrates its own `auth` schema on start.
- The operator wipes and redeploys: invalidated sessions are not a migration concern.
- ~15 API comments and tests say "read on GoTrue v2.195.0" (`modules/auth/auth-server-calls.ts`,
  `auth.service.ts`, `read-only-link.ts`, `sign-in-methods.ts`, `signup-account.ts`,
  `person-email-change`, and their tests). Unit tests use doubles, so they stay green whatever the
  real server now answers.

## Approach

Probe first, then bump. A throwaway GoTrue 2.198 (+ its postgres) runs locally under its own
compose project name, never the stack's container names. A probe script replays each pinned
behaviour (what request, which answer the code relies on) and prints 2.195-expected vs 2.198-actual.
Every difference is either harmless (comment re-dated) or a code fix with a test that goes red
first. Then the image tag changes in both compose files, the docs that name 2.195 are updated
(README, ARCHITECTURE table and §28, `tests/e2e/README.md`), and spec 48 asserts: `GET /user` still
200 for a connector token (temporary, named), `PUT /user` and `/user/oauth/grants` → 403
`no_authorization`.

Considered: (a) bump blind and let the e2e find breaks after deploy — rejected, the pinned answers
guard sign-in and password reset for every user; (b) the reauthentication flag or an edge refusal on
2.195 — rejected by the operator's choice to update.

## Left to the builder

- How the throwaway GoTrue is run (its own compose file in scratch, or `docker run`), as long as it
  never touches `myclash-*` names or volumes and is removed afterwards.
- The exact probe list, derived from the "read on GoTrue v2.195.0" sites.

## Verification

The probe output (all pinned answers, before/after); any fix's red-then-green test; the full
`myclash-gates` chain; `pnpm infra:review` (if it pins the tag); CI's start check
(`scripts/check-api-boot.sh`) locally if Docker allows; spec 48 after the operator deploys.
