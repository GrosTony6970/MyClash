# GoTrue 2.195 → 2.198 — design (small change)

Status: built 2026-11-24 (branch `feat/mcp-server`); the operator may hold the merge until 2026-11-30.

## Why

On GoTrue 2.195 a Claude connector token (an OAuth-server access token) can call GoTrue's own
`PUT /auth/v1/user` (password and email change), `/user/identities`, `/user/oauth/grants`,
`/factors`, `/logout`. MyClash's wall (MCP spec, call A) cannot reach GoTrue. 2.198 restricts OAuth
client tokens to the OAuth endpoints plus read-only `GET /user` (`403 no_authorization` otherwise).
This closes the MCP spec's Review Focus 1 / operator decision 1 before OAuth goes live.

## Goals

- `infra/docker-compose.prod.yml` and `infra/docker-compose.dev.yml` run `supabase/gotrue:v2.198.0`.
- Every place the API pins a GoTrue answer still holds on 2.198 — proven against a real 2.198, not
  assumed.
- The connector e2e records the new refusals.

## Non-goals

- No other Supabase service bumped (realtime, storage, PostgREST, postgres stay as they are).
- No use of 2.196–2.198 features (MFA recovery codes, SCIM, passkeys).
- No move of anything to `GET /oauth/userinfo` (MyClash never calls `/user` with a connector token).

## Constraints

- Timing: 2.198.0 is 8 days old (published 2026-11-16), but Supabase's own self-hosted
  `docker/docker-compose.yml` pins `supabase/gotrue:v2.198.0` — taken as the soak signal. Claude's
  call; the operator may hold the merge until 2026-11-30.
- Releases crossed: 2.196 (email identity created on first password set, behind an experimental
  flag for the user path; email-change and identity-unlink fixes), 2.197 (MFA recovery codes, SCIM
  tables, `one_time_tokens.expires_at`), 2.198 (OAuth-token restriction; password cleared on recover;
  one-time tokens become the source of truth; legacy null-aal sessions invalidated; after-user-created
  hook only on creation). GoTrue migrates its own `auth` schema on start.
- The operator wipes and redeploys: invalidated sessions are not a migration concern.
- ~15 API comments and tests say "read on GoTrue v2.195.0" (`modules/auth/auth-server-calls.ts`,
  `auth.service.ts`, `read-only-link.ts`, `sign-in-methods.ts`, `signup-account.ts`,
  `person-email-change`, and their tests). Unit tests use doubles, so they stay green whatever the
  real server now answers.

## Approach

Probe first, then bump. A throwaway GoTrue 2.198 (+ its postgres) runs locally under its own
compose project name, never the stack's container names. A probe script replays each pinned
behaviour (what request, which answer the code relies on) and prints 2.195-expected vs 2.198-actual.
Every difference is either harmless (comment re-dated) or a code fix with a test that goes red
first. Then the image tag changes in both compose files, the docs that name 2.195 are updated
(README, ARCHITECTURE table and §28, `tests/e2e/README.md`), and spec 48 asserts: `GET /user` still
200 for a connector token (temporary, named), `PUT /user` and `/user/oauth/grants` → 403
`no_authorization`.

Considered: (a) bump blind and let the e2e find breaks after deploy — rejected, the pinned answers
guard sign-in and password reset for every user; (b) the reauthentication flag or an edge refusal on
2.195 — rejected by the operator's choice to update.

## Left to the builder

- How the throwaway GoTrue is run (its own compose file in scratch, or `docker run`), as long as it
  never touches `myclash-*` names or volumes and is removed afterwards.
- The exact probe list, derived from the "read on GoTrue v2.195.0" sites.

## Verification

The probe output (all pinned answers, before/after); any fix's red-then-green test; the full
`myclash-gates` chain; `pnpm infra:review` (if it pins the tag); CI's start check
(`scripts/check-api-boot.sh`) locally if Docker allows; spec 48 after the operator deploys.

## Probe results (2026-11-24)

A throwaway compose project (`gotrue-probe`, scratch folder, not committed) ran GoTrue v2.195.0
(port 19195) and v2.198.0 (port 19198) side by side, each on its own `supabase/postgres:17.6.1.160`
with prod's four `infra/db/init/*.sh` scripts mounted read-only. GoTrue logs in as
`supabase_auth_admin`, as in prod. Its env is prod's auth env (password policy, refresh rotation and
reuse interval 10, `JWT_EXP=3600`, `MAILER_AUTOCONFIRM=false`, the OAuth server keys), with three
probe-only values: a throwaway JWT secret, SMTP pointed at `127.0.0.1:2`, and
`GOTRUE_MAILER_OTP_EXP=10` on BOTH versions so P1 sees a code expire by time. Both versions booted
and migrated (70 and 77 migrations). The stack was removed with `down -v` afterwards.

Commands:

```sh
docker compose -p gotrue-probe --env-file probe.env -f compose.yml up -d
node probe.mjs probe.env http://127.0.0.1:19195 http://127.0.0.1:19198
docker compose -p gotrue-probe --env-file probe.env -f compose.yml down -v
```

Every 2.195 row matches the comment at its code site, except one clause that was not probed. P6
cannot show the comment's "empty list for an account with no identity": the admin API makes no
such account on either version.

Differences:

- P8: on 2.198 a recovery link spent on an UNCONFIRMED account wipes the password that account
  had (GoTrue #2887). A confirmed account keeps its password, as on 2.195. Almost no API site is
  hit: the signup door sets no password (`signup-account.ts:53`, and P7 shows the
  `generateLink('signup')` password is not stored), and both admin creates set
  `email_confirm: true`. One door is the exception: the super admin's temporary password
  (`admin-users.service.ts`, `regenerateTempPassword`) writes a known password and confirms
  nothing; `auth.service.ts` calls it "the one door that gives an unconfirmed account a password
  she knows". On 2.198 a recovery link spent on such an account wipes the temporary password. The
  reset door writes the new password right after it spends the link, so the only bad case is that
  write failing after the spend: she is left with no password and a dead link, where 2.195 kept
  the temporary password. This is a known narrow window; no code changes for it. Review Focus 1's
  fear (a person loses her password by opening a reset link) does not hold for a confirmed
  account.
- P12: on 2.198 a connector token is refused (403 `no_authorization`) at `PUT /user`,
  `/user/oauth/grants` and `/logout`; `GET /user` still answers 200. It hits the spec Goal and
  Task 3's connector e2e (spec 48), as intended. No API site sends a connector token there. The
  probe sent no `X-Supabase-Api-Version` header, so the body read was `error_code:
"no_authorization"` with a numeric `code: 403`. The header form was not probed. Task 3's e2e
  sends no version header and asserts `error_code === 'no_authorization'`.
- P6 (not a difference, a gap): Task 2 does not re-date the empty-list clause at
  `sign-in-methods.ts:18-20`; it says the clause was read on 2.195 and not probed on 2.198.

### Not probed

- `DELETE /user/oauth/grants?client_id=` with a browser token (Disconnect). The connector e2e
  (spec 48) covers it after deploy.
- 2.196's "email tokens revoked when the email is replaced": what a link to the old address
  answers after an admin address change. A 4xx reads as "link expired", which is fine; a 5xx
  would read as "try again".
- 2.196's email identity on a first admin password. It is invisible on a `createUser` account,
  which already has an `email` identity. It matters only for a Google-only account that sets a
  password: `signsInWithPassword` then flips to true, which is the right direction.
